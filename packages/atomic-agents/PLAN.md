# atomic-agents: plan

Replace skills with atomic specialist agents. A **component** = one narrow agent (small prompt, its knowledge, its tools, best model) + its jobs (manual, cron, on-event) + an output contract of typed events. Assistants and Relay subscribe to events instead of the 30-minute `eva-heartbeat` sweep.

**Built (v0, Effect 4.1.4 LTS, Bun, own install, opt-in):** `Component.ts` contract (`define`, `job`; `Trigger` is a `Data.TaggedEnum` of `Manual`/`Cron`/`OnEvent`, and `OnEvent(contract, "<event>")` takes a declared event name, so a typo does not compile; a component's tools layer, knowledge file included, is built once per runtime), `Event.ts` (`AgentEvent` envelope, `EventBus`: append-only `~/.config/relay/atomic-agents/events.ndjson` (`ATOMIC_AGENTS_HOME`, Relay's data dir) tailed every 50 ms into a `PubSub`; the file is the cross-process bus; `listen` subscribes eagerly for request/response; bad lines are logged and skipped; the lifecycle events `job.started|job.succeeded|job.failed` are declared once as `Schema.TaggedStruct`s joined in `Lifecycle`, carry `_tag` in `data`, and `lifecycle(event)` decodes any envelope, older lines included), `Settings.ts` (the consumer config, below), `Model.ts` (`ModelRunner.omp`: `omp -p --mode json` with no tools, skills, rules or repo context, so swapping models is one string; reports served provider and cost; `openrouter/<vendor>/<model>` ids use omp's openrouter provider with the key from config `openRouterKeyFile` (or `OPENROUTER_API_KEY`), the key reaches no other call, and Anthropic/OpenAI ids are refused on OpenRouter), `Runtime.ts` (`Runner`: one run at a time per component, the `Lifecycle` events around every run, each run resolves its model from the config in force; `Runner.layerTriggers` arms cron and event triggers and re-arms crons when config changes), `Background.ts` (serve is two background layers, `Settings.layerWatch` and `Runner.layerTriggers`, forking into one `Background` fiber set the host joins: recoverable errors such as a disabled component or a bad `config.set` are logged, a `JournalError` ends serve and launchd restarts it), `Id.ts` (run and event ids and all timings come from `Clock` and `Random`, so `TestClock` drives crons in tests; `bun test`), `Service.ts` (`serve` as its own LaunchAgent `ai.eva.atomic-agents`, KeepAlive, log `<home>/logs/serve.log`; `service install` copies the package into `<home>/app/atomic-agents` and the chat-core sources it imports (`file:../chat-core`) into `<home>/app/chat-core`, and installs production deps there, so the service never runs from a checkout; `service install|uninstall|status`), `Ask.ts` (request/response, below), `cli.ts` (`list run bench rate wins use emit ask events serve service`). Pilot: **prop-render**, an object description → Blender `build()` script → GLB of the bare model plus a render on a fixed stage (floor, three lights, auto-framed camera) → `prop-render/render.completed {image, glb, script, model, attempts, seconds, cost}`. It retries once with Blender's traceback. Why this pilot: the result can be judged at a glance, it runs locally in about 2 s plus the model call, and since the stage is fixed only the model varies.

**Core vs consumer (Isaac, 2026-11-14):** the core (runtime, bus, model runner, built-in components with code defaults) lives here. The consumer side lives in `~/.config/relay/atomic-agents`: `config.json`, `events.ndjson`, `runs/`, `logs/`, `app/`. `config.json` (Effect Schema `SettingsFile`, strict: unknown keys, components, jobs and bad crons are rejected) holds `openRouterKeyFile` and per component `enabled`, `model`, `candidates`, `thinking`, `cron: {<job>: "<expr>"}`; absent keys fall back to the code defaults. **Live:** the service polls the file every second; a valid edit swaps in atomically, a bad one keeps the last good config and emits `atomic-agents/config.rejected`. Every applied change emits `atomic-agents/config.changed {by, source: use|set|file, changes: [{path, old, new}], undo, config}`; `undo` is a JSON merge patch (RFC 7396) that restores the old values. Changing config: `atomic-agents use <component> <model> [--by <who>]` (what a bake-off winner does; `wins` prints the command), or emit `atomic-agents/config.set {by, patch}` (merge patch) for the service to apply; emitting a `config.changed`'s `undo` as `config.set` reverts it.

**Second component: gmail (2026-11-14, shadow mode).** The first one whose model drives its own tools. Job `triage` (Manual + Cron `*/30 * * * *`, override `components.gmail.cron.triage`): a fixed step fetches inbound mail of Isaac's personal Gmail (`[Gmail]/All Mail`, not sent, drafts or chats) after the cursor in `<home>/state/gmail/cursor.json` (`{validity, uid}`; none or a new UIDVALIDITY starts from the last 24 h; at most 40 per run, oldest first; the cursor moves past each message once its event is written, so a failure resumes there). `mail.py` reuses the heartbeat's IMAP login (`jobs/eva-heartbeat/scripts/gmail.py`, `secrets/gmail.env`, under `EVA_ROOT`, default `~/Eva`), examines All Mail read-only and peeks bodies, so it cannot mark read, label, archive, send or delete. Per message the agent answers `needs_isaac | fyi | noise` with a one-line reason and a card title, guided by Nova's `catchup-taste.md` and `catchup-rules.json` (read every run) and two read-only tools, `read_thread(id)` and `sender_history(address)`. Tool calling is `generateWithTools` in `Model.ts`: a JSON tool loop over `ModelRunner.generate` (omp runs custom tools only through extensions inside its own process, so the loop keeps tools as the component's Effect services and works for every model): each reply is one `{"tool", "args"}` or `{"answer"}`, a tool outside the list never runs and the model is told what it may call, at most 3 model calls per message, then `ToolLoopError`. Events: `gmail/message.triaged {id (Message-ID, as the heartbeat), from, subject, date, verdict, reason, title}` per message and `gmail/triage.completed {messages, modelCalls, cost, replay}` per run. Input `{ids: [Message-ID]}` replays those messages without touching the cursor; that is what `bench gmail triage` runs, scored by `src/components/gmail/score.ts` (agreement with Isaac's Gmail Catch Up notes, when any exist, and with a reference run). Nothing routes these events yet: the heartbeat's Gmail source and Nova routing are unchanged until the shadow comparison is in.

**Third component: widget (2026-11-14), and request/response.** Purpose: "Given Nova's draft reply and its data, return the right Relay widget block for it, or none." Input `widget/widget.requested {requestId, draft, data?, surface: phone|desktop}`, output `widget/widget.ready {requestId, kind: openui|none, block?, why}`. Job `pick` (OnEvent on the request, plus Manual): one model call with a small prompt, Nova's WHEN rules (`.omp/response-formats/v2.md` § Widgets: default prose, Markdown table for 3+ items on 2+ fields, stat, chart, tickets, diff, compare, recipe, media, tabs of code, buttons) plus the component signatures read from chat-core's `relayLibrary`, so the prompt cannot drift from the parser. Reply format `why: <line>` then `none` or the program; chatter before the first statement is cut. Fixed final check: chat-core `parseOpenUI` (the parser Relay's phone and desktop render with); a program with a blocking error (a dropped node, unresolved name, no root) goes back once with the parser's errors, and if it still fails the answer is `none`, so no unparseable block ever goes out. A failed model call still answers `none` at once, then the run fails as usual. chat-core is a `file:../chat-core` dependency, so `bun install` refreshes the copy in node_modules after chat-core changes. **Request/response** (`Ask.ts`, generic): a component declares `asks: {request, reply, show}`; `ask(contract, pair, data, timeout)` listens, emits the request with a fresh `requestId` and returns the first reply carrying it, else `AskTimeout`. CLI: `atomic-agents ask widget '{"draft": ..., "surface": "phone"}' --timeout 5s` prints the block or `none` (exit 1 on timeout), timing on stderr. The bus adds about 60 ms per ask (tail 50 ms, OnEvent triggers subscribe before serve is up).

**Next, in order:**
1. **Test Bench:** `bench` runs one input across the candidates; `rate <run-a> <run-b> a|b|tie` writes a pairwise `pair.picked` event (as in the 2026-10-28 reel bench), `wins` prints each model's win rate (ties count half) and the `use` command that promotes the winner into config.json. Then add an `exp`-format writer (`work/experiments/<date>-prop-render/`) so the existing read-only Test Bench page lists the arms, and add a side-by-side A/B pick to the arm panel.
2. **Relay:** the host tails the journal and broadcasts `agents.event` frames (phone and desktop), and assistants get a per-assistant subscription list (`agents.json` `subscribes: ["prop-render/render.completed"]`) delivered through the existing `/assistant/say`.
3. **Migration:** move one heartbeat source at a time into a component whose cron job emits `<source>.item` events (Gmail runs in shadow as the `gmail` component; next compare it with the heartbeat's Gmail items, then the Slack collector in `jobs/eva-heartbeat/scripts/sweep.ts`). Then delete that source's branch from `SOURCE_AGENT`. Visual skills next (`ui-check`, as a ui-review component), then retire each skill once its component wins its bake-off.
