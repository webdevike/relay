# atomic-agents: plan

Replace skills with atomic specialist agents. A **component** = one narrow agent (small prompt, its knowledge, its tools, best model) + its jobs (manual, cron, on-event) + an output contract of typed events. Assistants and Relay subscribe to events instead of the 30-minute `eva-heartbeat` sweep.

**Layout (2026-11-16): one folder per domain.** `src/core/` is the shared runtime every domain uses (components, agent files and specs, adapters contract, bus, model runner, runtime, settings, orchestrators, service, code mode) plus the adapters several domains share (`src/core/adapters/`: the harnesses `omp.ts`, `codex.ts` and `claude-code.ts` for model calls, `eva.ts` Eva's root). `src/cli.ts` and `src/packs.ts` (every pack the CLI and service load) are the composition root. Each `domains/<domain>/` is one bounded context: its agent files (and their knowledge), `adapters/`, `bench/` and `test/`, with `index.ts` as its only public entry; domains never import each other. Domains: `design` (design-critic, browser, ui-check), `ecard` (the ecard-* agents), `gmail`, `render` (prop-render, Blender), `research` (web-researcher, Muse, agent-reach), `widget` (widget, OpenUI). The loader reads built-in agents from every `domains/*/` and then `<home>/agents/`. Vocabulary: an **agent** is one component, defined by an **agent file** (`<id>.json|yaml`) holding an **agent spec** (`AgentSpec.ts`) or pointing at code (`kind: "code"`); a spec agent's **model stage** is what benches call without the bus.

**Built (v0, Effect 4.1.4 LTS, Bun, own install, opt-in):** `Component.ts` contract (`define`, `job`; `Trigger` is a `Data.TaggedEnum` of `Manual`/`Cron`/`OnEvent`, and `OnEvent(contract, "<event>")` takes a declared event name, so a typo does not compile; a component's tools layer, knowledge file included, is built once per runtime), `Event.ts` (`AgentEvent` envelope, `EventBus`: append-only `~/.config/relay/atomic-agents/events.ndjson` (`ATOMIC_AGENTS_HOME`, Relay's data dir) tailed every 50 ms into a `PubSub`; the file is the cross-process bus; `listen` subscribes eagerly for request/response; bad lines are logged and skipped; the lifecycle events `job.started|job.succeeded|job.failed` are declared once as `Schema.TaggedStruct`s joined in `Lifecycle`, carry `_tag` in `data`, and `lifecycle(event)` decodes any envelope, older lines included), `Settings.ts` (the consumer config, below), `Model.ts` (`ModelRunner.omp`: `omp -p --mode json` with no tools, skills, rules or repo context, so swapping models is one string; reports served provider and cost; `openrouter/<vendor>/<model>` ids use omp's openrouter provider with the key from config `openRouterKeyFile` (or `OPENROUTER_API_KEY`), the key reaches no other call, and Anthropic/OpenAI ids are refused on OpenRouter), `Runtime.ts` (`Runner`: one run at a time per component, the `Lifecycle` events around every run, each run resolves its model from the config in force; `Runner.layerTriggers` arms cron and event triggers and re-arms crons when config changes), `Background.ts` (serve is two background layers, `Settings.layerWatch` and `Runner.layerTriggers`, forking into one `Background` fiber set the host joins: recoverable errors such as a disabled component or a bad `config.set` are logged, a `JournalError` ends serve and launchd restarts it), `Id.ts` (run and event ids and all timings come from `Clock` and `Random`, so `TestClock` drives crons in tests; `bun test`), `Service.ts` (`serve` as its own LaunchAgent `ai.eva.atomic-agents`, KeepAlive, log `<home>/logs/serve.log`; `service install` copies the package into `<home>/app/atomic-agents` and the chat-core sources it imports (`file:../chat-core`) into `<home>/app/chat-core`, and installs production deps there, so the service never runs from a checkout; `service install|uninstall|status`), `Ask.ts` (request/response, below), `cli.ts` (`list run bench rate wins use emit ask events serve service`). Pilot: **prop-render**, an object description → Blender `build()` script → GLB of the bare model plus a render on a fixed stage (floor, three lights, auto-framed camera) → `prop-render/render.completed {image, glb, script, model, attempts, seconds, cost}`. It retries once with Blender's traceback. Why this pilot: the result can be judged at a glance, it runs locally in about 2 s plus the model call, and since the stage is fixed only the model varies.

**Core vs consumer (Isaac, 2026-11-14):** the core (runtime, bus, model runner, built-in components with code defaults) lives here. The consumer side lives in `~/.config/relay/atomic-agents`: `config.json`, `events.ndjson`, `runs/`, `logs/`, `app/`. `config.json` (Effect Schema `SettingsFile`, strict: unknown keys, components, jobs and bad crons are rejected) holds `openRouterKeyFile` and per component `enabled`, `model`, `candidates`, `thinking`, `toolMode: tools|code` (only for an agent with tools; when to pick which: [`docs/code-mode.md`](docs/code-mode.md)), `cron: {<job>: "<expr>"}`; absent keys fall back to the code defaults. **Live:** the service polls the file every second; a valid edit swaps in atomically, a bad one keeps the last good config and emits `atomic-agents/config.rejected`. Every applied change emits `atomic-agents/config.changed {by, source: use|set|file, changes: [{path, old, new}], undo, config}`; `undo` is a JSON merge patch (RFC 7396) that restores the old values. Changing config: `atomic-agents use <component> [<model>] [--tool-mode tools|code] [--by <who>]` (what a bake-off winner does; `wins` prints the command), or emit `atomic-agents/config.set {by, patch}` (merge patch) for the service to apply; emitting a `config.changed`'s `undo` as `config.set` reverts it.

**Third component: widget (2026-11-14), and request/response.** Purpose: "Given Nova's draft reply and its data, return the right Relay widget block for it, or none." Input `widget/widget.requested {requestId, draft, data?, surface: phone|desktop}`, output `widget/widget.ready {requestId, kind: openui|none, block?, why}`. Job `pick` (OnEvent on the request, plus Manual): one model call with a small prompt, Nova's WHEN rules (`.omp/response-formats/v2.md` § Widgets: default prose, Markdown table for 3+ items on 2+ fields, stat, chart, tickets, diff, compare, agent spec, media, tabs of code, buttons) plus the component signatures read from chat-core's `relayLibrary`, so the prompt cannot drift from the parser. Reply format `why: <line>` then `none` or the program; chatter before the first statement is cut. Fixed final check: chat-core `parseOpenUI` (the parser Relay's phone and desktop render with); a program with a blocking error (a dropped node, unresolved name, no root) goes back once with the parser's errors, and if it still fails the answer is `none`, so no unparseable block ever goes out. A failed model call still answers `none` at once, then the run fails as usual. chat-core is a `file:../chat-core` dependency, so `bun install` refreshes the copy in node_modules after chat-core changes. **Request/response** (`Ask.ts`, generic): a component declares `asks: {request, reply, show}`; `ask(contract, pair, data, timeout)` listens, emits the request with a fresh `requestId` and returns the first reply carrying it, else `AskTimeout`. CLI: `atomic-agents ask widget '{"draft": ..., "surface": "phone"}' --timeout 5s` prints the block or `none` (exit 1 on timeout), timing on stderr. The bus adds about 60 ms per ask (tail 50 ms, OnEvent triggers subscribe before serve is up).

**Agents are config (2026-11-15).** A component ("agent") is a file, `<id>.json` or `.yaml` (`Agent.ts`, Effect Schema, strict): built-ins ship in the package's `domains/<domain>/`, Isaac's own in `<home>/agents/` (same id replaces a built-in). The service re-reads both every second: `atomic-agents/agent.loaded {id, file, kind, replaced}`, `agent.removed`, and a bad file is `config.rejected` naming the file and every reason while the last good version keeps running. A file follows the standard agent spec (`AgentSpec.ts`): `trigger -> [source] -> [steps] -> model (+ tools, maxSteps) -> [check, one repair turn] -> output event` (plus an optional once-per-run `summary` event and `onFailure` fields), with event and answer fields in a small type language (`Fields.ts`: `string`, `nonEmptyString`, `int`, `number`, `boolean`, `json`, `{"enum": [...]}`, `{"array": T}`, objects, `key?` optional). Everything it names is an **adapter** (`Adapter.ts`, packs registered by name in `src/core/Adapter.ts`, packs in each domain's `adapters/`, built once per process); an unknown name, a prompt `{{field}}` nothing provides, or an output field nothing fills fails at load, never at run time. Adapters today: harnesses (`agent.harness`) `omp`, `codex`, `claude-code`; tools `gmail.read_thread`, `gmail.sender_history`; sources `gmail.new_since_cursor`, `browser.screenshot`; checks `openui.parse` (its contract, the parser's signatures, goes in the prompt as `{{check}}`), `blender.render`, `ui-check.evidence`; step `widget.prompt`. Triggers stay `manual`, `{cron, input | inputs (rotating daily)}`, `{onEvent}`. Escape hatches: a `steps` entry (named code inserted before the model), or `kind: "code"` with `module` and `export` pointing at a `define()`d component. widget, gmail and prop-render are all agent spec files now (prop-render's retry loop is `blender.render`'s repair turn); prompts are byte-identical to the code versions (knowledge files are appended trimmed). **Add an agent:** `atomic-agents agent new <id>` (a working request/reply agent spec in `<home>/agents`), edit it, `atomic-agents agent validate`; the service picks it up without a restart. A missing capability is a new adapter in a pack, not agent code. config.json entries for an agent that is not loaded are kept and apply once it loads.
Benches live in each domain's `bench/` (`widget.ts` calls the widget agent's model stage, `Agent.modelStage`, `widget-cases.ts|json`, `gmail-score.ts`); the old components dir and `builtins.ts` are gone (code agents live wherever their `kind: "code"` file points).

**Backup model (2026-11-17).** `config.json` `components.<id>.fallbackModel` (`atomic-agents use <id> <model> --fallback <model>`, or `config.set`; a `config.changed` event with undo like any setting).
