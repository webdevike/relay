## Phase Goal

**As a** EvaOS user, **I want to** see and act on my Eva data (workspaces, todos, jobs, habits, meetings) from the new app, **so that** I can work from it daily while every write to the Eva checkout still goes through EvaFs.

<objective>
Slice: act on meeting proposals. Accept turns a proposal into a todo; Dismiss closes it; both write only through EvaFs and are safe against double clicks and concurrent edits.

Purpose: MEET-03 and CONTEXT "Accept appends a todo via EvaFs; Dismiss writes the record's status field via EvaFs." D13 settled: the written field is `proposals[i].status` (Rust), which is what "the record's status field" means. Write format follows meeting-memory.ts (`JSON.stringify(value, null, 2)` plus newline, insertion order kept), smaller diffs than the Rust app's alphabetized rewrite.
Output: accept and dismiss handlers, UI actions on Detail and Home, e2e with file assertions and proof.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-65 | Tampering | duplicate todos from double accept | mitigate | per-stem serialized accept with the proposed pre-check; setProposalStatus refuses non-proposed |
| T-03-66 | Tampering | markdown injection via proposal text or workspace | mitigate | appendTodo collapses newlines; workspace tag sanitized to a safe id or eva |
| T-03-67 | Tampering | record rewrite dropping fields | mitigate | parse, change one status, stringify in insertion order; e2e checks keys and extra fields |
| T-03-68 | Repudiation | half-done accept | mitigate | 'partial-accept' error names the new todo id; the UI shows it and offers Reload |
</threat_model>
